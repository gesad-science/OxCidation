# Research Diary: C to Rust Translation Agent
**Date**: 2026-06-15

## General System Pipeline Structure
The current testing framework is designed to evaluate the capability of Small Language Models (SLMs) running locally (e.g., via Ollama) or commercial APIs to accurately translate C competitive programming solutions into Rust. 

The architecture is composed of two primary layers:
1. **The Orchestrator (`tranformation_agent.py`)**: A LangGraph state machine that manages the lifecycle of each file. It cycles through `translate_node`, `compile_node`, and `test_node`. If the compiler or the I/O tests fail, it loops back to the `repair_node` for a maximum of 5 iterations.
2. **The MCP Sandbox (`server.py`)**: Executes prompt generation, compilation (`rustc`, `gcc`), and safe execution. Test matching is handled natively in Python using a `.split()` token comparison, replicating the strict input/output verification style of competitive programming judges (like `oj test`) without relying on third-party CLIs.

## Initial Results & Observations
During the initial batch tests of the first 20 CodeNet C samples, the agent successfully compiled the translated Rust code but frequently failed the behavioral I/O test cases, consistently triggering the maximum number of repair attempts. 

An inspection of the test logs (`logs/tests.log`) and execution traces (`logs/agent.log`) revealed that the Rust translations were functionally correct but contained extra "user-friendly" `println!` prompts (e.g., `println!("Enter 10 integers:");`). Because the pipeline enforces strict competitive programming output formatting, these extra text artifacts caused the `.split()` matching against the expected `.out` files to fail. 

## Changes & Adjustments Made
Based on the execution feedback, the following pipeline optimizations were implemented:

1. **Strict Behavioral Translation Prompt**: Replaced the simple translation instruction with a robust, hard-constraint prompt (`translation_prompt.txt`). The new prompt strictly forbids the LLM from adding new features, validation, prompts, or explanations, forcing it to maintain the exact algorithmic approach and I/O footprint of the original C code.
2. **Dedicated Test Analytics**: Shifted metrics generation to capture precise analytical data: C pass/fail counts vs Rust pass/fail counts. The pipeline now aggregates these statistics over the batch and exports a JSON summary directly to `logs/tests.log`.
3. **Internal Reasoning Toggle**: Added a `think: false` configuration to `config.yaml` to prevent Ollama reasoning models (like DeepSeek-R1) from polluting the code extraction process with internal reasoning blocks via the API. 
4. **Context Management**: Verified that LangChain is invoking prompts strictly in a zero-shot, stateless manner. The LLM only receives the most recent error context on repair loops, ensuring independent translation iterations.
