# OxCidation

OxCidation evaluates C-to-Rust translations generated by an LLM. A benchmark run selects accepted C submissions, generates one language-agnostic visible-test suite per program, translates each program with one or more prompts, and can run a reproducible C/Rust Judge comparison.

The unit of analysis is one accepted C submission per CodeNet problem. A prompt benchmark holds the model fixed and varies the C program and translation prompt.

## Prerequisites

- Python 3.10 or newer with the project's virtual environment at `.venv`.
- GNU `tar` for selective Project CodeNet archive extraction.
- `rustc` and `gcc` for the normal translation pipeline.
- `oj` from online-judge-tools for Judge execution.
- Podman for the reproducible Judge profile. The first containerized Judge run pulls the configured GCC and Rust images into Podman's local cache; it does not install compilers on the host.
- A local Project CodeNet checkout with `data`, `metadata`, and, when using sample-based Judge cases, `derived/input_output/data`.

All commands below are run from the repository root.

```bash
./.venv/bin/pip install -r requirements.txt
PYTHONPATH=src ./.venv/bin/python -m unittest discover -s tests -v
```

The first command installs the project dependencies, including `openpyxl` for the review workbook. Use the second command after code changes; it runs the unit tests and prints an `OK` summary when they pass.

## Configuration

The environment variable `OXCIDATION_CONFIG_FILE` selects the active model configuration. The file defines the provider, model, request pacing, repair limit, and visible-test settings.

`visible_test_time_limit_sec` controls local visible-test execution. The Judge timeout always comes from CodeNet's `metadata/problem_list.csv`; problems without a numeric CodeNet time limit are recorded as missing baseline data and are not evaluated.

### Gemini

The repository includes two Gemini profiles:

- `config/gemini-3.1-flash-lite.yaml`
- `config/gemma-4-31b-it.yaml`

Both profiles pace all LLM requests at 15 RPM, including visible-test generation, translation, semantic validation, and repair. Export `GEMINI_API_KEY` for the command that launches the benchmark.

```bash
GEMINI_API_KEY="..." \
OXCIDATION_CONFIG_FILE=config/gemini-3.1-flash-lite.yaml \
./.venv/bin/python src/benchmark.py --help
```

This only displays the benchmark options. It does not call Gemini or create an experiment directory.

### OpenAI

Create a configuration file such as `config/openai-benchmark.yaml` with the model selected for the experiment:

```yaml
provider: openai
model: gpt-4.1-mini
request_rate_limit_rpm: 0
max_repair_attempts: 5
judge_backend: auto
visible_test_time_limit_sec: 5
judge_compare_mode: ignore-spaces-and-newlines
```

Then provide `OPENAI_API_KEY` and point `OXCIDATION_CONFIG_FILE` at that profile:

```bash
OPENAI_API_KEY="..." \
OXCIDATION_CONFIG_FILE=config/openai-benchmark.yaml \
./.venv/bin/python src/benchmark.py --help
```

Set `request_rate_limit_rpm` to the documented rate limit of the chosen OpenAI account and model. The benchmark uses one model per experiment; compare prompts within the same experiment or across separately recorded experiments.

## Build a CodeNet Population Manifest

### Extract the complete accepted-C subset

Use `extract_accepted_codenet.py` when starting from the full compressed Project CodeNet distribution:

```bash
./.venv/bin/python extract_accepted_codenet.py \
  --archive /path/to/CodeNet/Project_CodeNet.tar.gz \
  --output /path/to/CodeNet/Project_CodeNet_C_Accepted
```

The extractor reads the archive twice. The first pass reads metadata and identifies every row with `language=C`, `status=Accepted`, and `filename_ext=c`. The second pass scans the archive once, extracts the C section and supporting data, and removes every C source not present in the accepted-submission set. The final subset contains no rejected C submissions or other programming languages.

Because a compressed tar archive has no random-access index, the second pass must read and decompress the complete archive even though it writes only the C section. The command prints an activity message every minute while this pass is running. If interrupted, it removes its partial staging directory before exiting.

The output preserves the relevant CodeNet layout:

```text
Project_CodeNet_C_Accepted/
  data/<problem_id>/C/<submission_id>.c
  metadata/<problem_id>.csv
  metadata/problem_list.csv
  problem_descriptions/<problem_id>.html
  derived/input_output/data/<problem_id>/{input.txt,output.txt}
  manifests/accepted_c_submissions.csv
  manifests/problems.csv
  extraction_summary.json
  SUBSET_README.md
```

Per-problem metadata is filtered to extracted accepted C submissions. `manifests/accepted_c_submissions.csv` contains every verified source and is the appropriate input for counting the complete population. `manifests/problems.csv` gives one row per problem with its accepted-C count and description/sample-I/O availability.

The extracted `input.txt` and `output.txt` files are the first samples found in each problem description. They are preserved for visible-test and coverage analysis, but they are not a full hidden-test Judge suite. The extractor also preserves CodeNet's verified/unverified sample-I/O classification.

The output path must not already exist. This prevents an extraction from being mixed with an older or partial subset.

### Select one accepted C program per problem

Run `prepare_benchmark_population.py` after extraction when constructing the one-program-per-problem population used by the benchmark:

```bash
./.venv/bin/python prepare_benchmark_population.py \
  --data-root /path/to/CodeNet/Project_CodeNet_C_Accepted/data \
  --metadata-root /path/to/CodeNet/Project_CodeNet_C_Accepted/metadata \
  --output data/processed/benchmark_population.csv \
  --selection-seed 42
```

This does not extract the dataset. It selects one verified `Accepted` C submission per problem from the complete subset and writes:

- `data/processed/benchmark_population.csv`: the population manifest used by `src/benchmark.py`.
- `data/processed/benchmark_population.summary.json`: selection policy, seed, population size, and skipped-problem counts.

Use `--require-rust-accepted` only when reproducing the historical Gold Standard intersection in which each problem also has an accepted Rust submission:

```bash
./.venv/bin/python prepare_benchmark_population.py \
  --data-root /path/to/CodeNet/Project_CodeNet/data \
  --metadata-root /path/to/CodeNet/Project_CodeNet/metadata \
  --output data/processed/benchmark_population_gold.csv \
  --require-rust-accepted \
  --selection-seed 42
```

## Prefetch AOJ System Tests

Use `prepare_aoj_system_tests.py` to process the complete accepted-C problem manifest and build a reusable local Judge corpus for every retrievable problem:

```bash
./.venv/bin/python prepare_aoj_system_tests.py \
  --problem-manifest /path/to/CodeNet/Project_CodeNet_C_Accepted/manifests/problems.csv \
  --output-root /path/to/CodeNet/aoj_system_tests
```

The command deduplicates problems and downloads complete system suites for AIZU rows. AtCoder rows are retained in the final report with status `unsupported_dataset` because equivalent system-test access is not currently available.

By default, six problem workers share a global limit of eight HTTP requests per second. This overlaps API latency without allowing every worker to issue requests at the full rate. Use `--workers` and `--requests-per-second` to tune these limits when needed.

Downloads are resumable at the test-case level. Incomplete suites remain under `<output-root>/.partial/`; complete suites are published atomically under `<output-root>/<problem_id>/`. On restart, completed files are verified by size and SHA-256 hash and are not requested again. Pressing `Ctrl+C` stops new requests after in-flight requests finish.

Retry only rows still classified as `failed` with:

```bash
./.venv/bin/python prepare_aoj_system_tests.py \
  --problem-manifest /path/to/CodeNet/Project_CodeNet_C_Accepted/manifests/problems.csv \
  --output-root /path/to/CodeNet/aoj_system_tests \
  --retry-failed-from /path/to/CodeNet/aoj_system_tests/prefetch_results.csv
```

The targeted retry merges its results into the existing complete report. AOJ headers that explicitly declare unavailable content are recorded as `unavailable`, not repeatedly treated as network failures. A one-byte excess caused by a returned terminal newline is accepted and recorded in the suite manifest; other size discrepancies remain failures for investigation.

For a small live check before starting the full population:

```bash
./.venv/bin/python prepare_aoj_system_tests.py \
  --problem-manifest /path/to/CodeNet/Project_CodeNet_C_Accepted/manifests/problems.csv \
  --output-root /path/to/CodeNet/aoj_system_tests \
  --limit 5
```

The output root contains:

- `pNNNNN/suite_manifest.json`: source URLs, retrieval time, byte counts, hashes, and per-case fallback information.
- `pNNNNN/*.in` and `pNNNNN/*.out`: the validated test suite consumed by the existing Judge.
- `prefetch_results.csv`: one status row per processed problem.
- `prefetch_summary.json`: status totals, case count, and downloaded byte totals for the latest run.

Point the benchmark's `--judge-tests-root` option at this output root. AOJ cases remain exclusive to the observational Evaluator and must not enter visible-test generation or repair feedback.

## Run a Translation Benchmark

Use this command when comparing translation prompts for one selected model. `--experiment-id` must be new, except for an empty directory left by an early configuration failure.

### Gemini benchmark with integrated Judge

```bash
GEMINI_API_KEY="..." \
OXCIDATION_CONFIG_FILE=config/gemini-3.1-flash-lite.yaml \
./.venv/bin/python src/benchmark.py \
  --experiment-id gemini-flash-lite-smoke-08 \
  --input-dir /path/to/CodeNet/Project_CodeNet/data \
  --source-manifest data/processed/benchmark_population.csv \
  --prompts-dir prompts/benchmark \
  --sample-size 20 \
  --seed 42 \
  --judge-tests-root /path/to/CodeNet/Project_CodeNet/derived/input_output/data \
  --metadata-root /path/to/CodeNet/Project_CodeNet/metadata
```

### OpenAI benchmark with integrated Judge

```bash
OPENAI_API_KEY="..." \
OXCIDATION_CONFIG_FILE=config/openai-benchmark.yaml \
./.venv/bin/python src/benchmark.py \
  --experiment-id openai-smoke-01 \
  --input-dir /path/to/CodeNet/Project_CodeNet/data \
  --source-manifest data/processed/benchmark_population.csv \
  --prompts-dir prompts/benchmark \
  --sample-size 20 \
  --seed 42 \
  --judge-tests-root /path/to/CodeNet/Project_CodeNet/derived/input_output/data \
  --metadata-root /path/to/CodeNet/Project_CodeNet/metadata
```

The benchmark first asks the configured model to generate concrete standard-input cases from each C source. The model chooses the suite size and never receives the problem statement or Judge cases. OxCidation executes the accepted C program to reject unusable inputs and produce the expected `.out` files.

It then performs the following work for every `program x prompt` pair:

1. Translates C to Rust and saves the raw response.
2. Compiles Rust and asks the Evaluator to record a Judge result for the initial translation.
3. Executes C and Rust against the same generated visible-test suite.
4. On a visible differential failure, asks the Validator whether the evidence represents a translation discrepancy or an invalid visible test.
5. Applies visible-test repairs when requested and records each code attempt.
6. Asks the Evaluator to record the final Judge result.

Valid translation discrepancies can trigger repair; invalid or unreliable visible-test evidence never modifies Rust and proceeds to independent Judge evaluation. Semantic repairs receive the original C source, current Rust translation, Validator guidance, and failure category.

Initial and final Judge results are observational. They are never sent to the Validator or Translator and cannot trigger repair. When no repair changes the code, the final Evaluator step reuses the initial Judge result instead of executing the same code twice.

The visible-test suite is generated once per C program and reused for every translation prompt and repair attempt. Reuse requires matching C-source and generation-prompt hashes. Its fixed prompt is stored in `prompts/visible_test_generation_prompt.txt`; translation prompts remain under `prompts/benchmark/`.

Prompt order is deterministically shuffled for each program using the experiment seed. `execution_order` and `prompt_position` preserve the request order, while analytical files remain sorted by stable program and prompt identifiers.

The integrated comparison first compiles and executes the original C program in a constrained container. Rust is evaluated only when C is accepted on the same Judge cases. This prevents invalid sample I/O, unsupported C baselines, or environment failures from being counted as translation failures.

The command prints the path to `results.csv` when the benchmark completes. It creates `outputs/<experiment-id>/` with:

- `manifest.json`: selected programs, prompts, model profile, and Judge profile.
- `results.csv`: one row per `program x prompt`, with explicit initial and final outcomes.
- `attempts.csv`: one row per initial translation or repair attempt.
- `summary.json`: aggregate outcomes by prompt.
- `review_workbook.xlsx`: blinded, linked workbook for two reviewers and adjudication.
- `runs.jsonl`: workflow records from the translation pipeline.
- `resume_history.jsonl`: one entry per accepted `--resume` invocation.
- `visible_tests/<submission_id>/<source-hash>/`: generated inputs, C oracle outputs, generation record, and suite manifest shared by all prompts.
- `model_outputs/<submission_id>/<prompt_id>/`: source C, initial/final Judge comparisons, versioned Rust attempts, raw response, final test/Validator reports, complete `agent_interactions.json`, and full result JSON.

`agent_interactions.json` is chronological and preserves every translation, compilation, visible-test report, Validator analysis and decision, repair request/response, and final Judge decision. The final `test_report.json` and `validator_report.json` remain convenience snapshots and may describe only the last successful attempt.

Each interaction records a sequence number, causal predecessor, agent, action, repair attempt, and action-specific data. Reports, compiler diagnostics, and code versions are stored once; later events refer to their causal predecessor instead of copying the same payload. This makes a failure loop directly traceable, for example: `visible_test_report` -> `semantic_analysis` -> `visible_test_decision` -> `repair` -> `compilation` -> `visible_test_report`. `semantic_analysis_skipped` explicitly identifies transitions where no LLM analysis occurred.

The CSV fields `validator_completed_analysis_count` and `validator_invalid_visible_test_count` report completed semantic analyses and rejected visible-test evidence respectively, while `agent_interactions_path` links to the complete history.

### Resume an interrupted benchmark

Use exactly the same command and add `--resume`:

```bash
GEMINI_API_KEY="..." \
OXCIDATION_CONFIG_FILE=config/gemini-3.1-flash-lite.yaml \
./.venv/bin/python src/benchmark.py \
  --experiment-id gemini-flash-lite-smoke-08 \
  --input-dir /path/to/CodeNet/Project_CodeNet/data \
  --source-manifest data/processed/benchmark_population.csv \
  --prompts-dir prompts/benchmark \
  --sample-size 20 \
  --seed 42 \
  --judge-tests-root /path/to/CodeNet/Project_CodeNet/derived/input_output/data \
  --metadata-root /path/to/CodeNet/Project_CodeNet/metadata \
  --resume
```

Resume is refused if source contents, selected programs, prompts, model settings, pipeline configuration, Judge profile, or implementation files differ from the original manifest. A combination is skipped only when its CSV row and complete artifact set are both valid; incomplete combinations are rerun without duplicate rows.

### Regenerate the review workbook

The benchmark creates the workbook on successful completion. Regenerate it after editing review-support CSV data with:

```bash
PYTHONPATH=src ./.venv/bin/python src/review_workbook.py \
  outputs/<experiment-id>
```

`Review Queue` uses blinded `review_id` values and presents only the principal initial/final outcomes and compact failure evidence. `Artifact Index` centralizes relative external links to source, code attempts, reports, interactions, and complete JSON results without displaying raw paths. `Automatic Results` and `Attempts` contain curated analytical fields rather than complete CSV mirrors. `Prompt Mapping` is hidden to avoid exposing prompt identity during review; unhide it when analysis is complete. `Reviews` contains two rows per result, and `Adjudication` records the third reviewer’s decision when required.

The C Judge profile uses `gcc:5.4` with `gcc -O2 -pipe source.c -o program -lm`. The Rust profile uses `rust:1.85.0-bookworm`. Per-problem time and memory limits come from `metadata/problem_list.csv`; the stack limit is set to the problem memory limit.

### Translation benchmark without a Judge profile

Omit both `--judge-tests-root` and `--metadata-root` when only translation, compilation, and the existing visible-test workflow are needed:

```bash
GEMINI_API_KEY="..." \
OXCIDATION_CONFIG_FILE=config/gemini-3.1-flash-lite.yaml \
./.venv/bin/python src/benchmark.py \
  --experiment-id gemini-translation-only-01 \
  --input-dir /path/to/CodeNet/Project_CodeNet/data \
  --source-manifest data/processed/benchmark_population.csv \
  --prompts-dir prompts/benchmark \
  --sample-size 20 \
  --seed 42
```

In this mode, the pipeline reaches the same Judge node, which returns `SKIPPED` because no CodeNet Judge profile was configured. It does not switch to a different Judge implementation.

## Re-evaluate an Existing Experiment

Use this command after fixing the Judge environment or when adding Judge cases to an experiment that was already translated. It does not call Gemini or OpenAI and does not regenerate translations.

```bash
OXCIDATION_CONFIG_FILE=config/gemini-3.1-flash-lite.yaml \
./.venv/bin/python src/evaluate_smoke_judge.py \
  --experiment-id gemini-flash-lite-smoke-07 \
  --evaluation-id judge-comparison-03 \
  --judge-tests-root /path/to/CodeNet/Project_CodeNet/derived/input_output/data \
  --metadata-root /path/to/CodeNet/Project_CodeNet/metadata
```

It returns a completion line with the generated CSV path and writes:

```text
outputs/<experiment-id>/judge_evaluations/<evaluation-id>/
  results.csv
  runs.jsonl
  summary.json
```

`results.csv` contains one row per existing benchmark result. `runs.jsonl` contains complete C and Rust compilation/Judge reports, including compiler output, verdict counts, first failure, and raw `oj` output. `summary.json` aggregates baseline, C, and Rust Judge statuses.

## Judge Case Layout

The Judge resolver accepts either layout below. It first checks the submission ID, then the problem ID.

```text
<judge-tests-root>/<submission_id>/case-1.in
<judge-tests-root>/<submission_id>/case-1.out
```

```text
<judge-tests-root>/<problem_id>/case-1.in
<judge-tests-root>/<problem_id>/case-1.out
```

It also accepts Project CodeNet's extracted sample layout:

```text
<judge-tests-root>/<problem_id>/input.txt
<judge-tests-root>/<problem_id>/output.txt
```

The sample layout represents one extracted example, not a full hidden-test Judge suite. A C baseline must still pass it before the Rust output is evaluated.
